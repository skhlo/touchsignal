# Upstream implementation research: Touch Bar candidates

Sources below are the named projects' upstream GitHub repositories and files, inspected 2026-08-29. Conclusions about fit are inferences from those sources.

## Decision summary

For this Intel/T2 Linux machine, treat the Touch Bar as a **single-owner DRM/KMS display plus a separate input device**. `react-drm-for-touchbar` is the only candidate explicitly built around that target and supports Hyprland's IPC for focused-window context, but it intentionally replaces `tiny-dfr` rather than coexisting with it. `tiny-dfr` is a mature small baseline and its configuration is suitable for static function/media keys, not application state. Reuse the **adapter/focus ownership pattern** from Microbridge or OpenMicro only conceptually: one state broker owns focus and routes commands to advertised adapters. Do not run any two display daemons.

## AsahiLinux/tiny-dfr

- It is a Rust, direct-DRM renderer using Cairo, `libinput`, and a `uinput` virtual keyboard. It takes DRM master to modeset and own the Touch Bar framebuffer, assigns a dedicated `seat-touchbar` plus `seat0`, finds the Touch Bar digitizer, and emits configured key actions through uinput. This is display and touch/input ownership, not a Wayland panel or a Hyprland client. [display backend](https://github.com/AsahiLinux/tiny-dfr/blob/master/src/display.rs) · [implementation](https://github.com/AsahiLinux/tiny-dfr/blob/master/src/main.rs) · [seat rules](https://github.com/AsahiLinux/tiny-dfr/blob/master/etc/udev/rules.d/99-touchbar-seat.rules)
- Its configuration is deliberately static and layered: `/etc/tiny-dfr/config.toml` overrides the packaged template field by field, and the daemon reloads it on change. It offers primary and media layers, button text/icons/time/battery, key or key-combo actions, layout stretch, brightness, pixel shift, and Fn/double-press behavior. It has no application-focus or IPC adapter mechanism. [configuration template](https://github.com/AsahiLinux/tiny-dfr/blob/master/share/tiny-dfr/config.toml) · [configuration loader](https://github.com/AsahiLinux/tiny-dfr/blob/master/src/config.rs)
- The service identifies itself as a tiny Apple T2 and Apple Silicon Touch Bar daemon; its udev rules cover `appletbdrm` (Intel/T2) as well as Apple Silicon. The template also uses a T2 battery calculation on `x86_64`. That confirms Intel/T2 applicability. [service](https://github.com/AsahiLinux/tiny-dfr/blob/master/etc/systemd/system/tiny-dfr.service) · [udev rules](https://github.com/AsahiLinux/tiny-dfr/blob/master/etc/udev/rules.d/99-touchbar-tiny-dfr.rules) · [configuration template](https://github.com/AsahiLinux/tiny-dfr/blob/master/share/tiny-dfr/config.toml)
- License: MIT for the project, with embedded Material icons under Apache-2.0; `Cargo.toml` declares `MIT AND Apache-2.0`. [README](https://github.com/AsahiLinux/tiny-dfr/blob/master/README.md) · [manifest](https://github.com/AsahiLinux/tiny-dfr/blob/master/Cargo.toml)
- Lifecycle uses udev-started systemd and `BindsTo` relationships to display/backlight devices with `Restart=always`, but lacks a documented suspend/resume hook. A current issue reports input events stopping until a service restart, so sleep/wake needs an explicit hardware test. [service](https://github.com/AsahiLinux/tiny-dfr/blob/master/etc/systemd/system/tiny-dfr.service) · [issue 33](https://github.com/AsahiLinux/tiny-dfr/issues/33)
- Fit/risk: the lowest-complexity function-row owner. It is not an extensible app-state renderer. Any richer service must either replace it or communicate only by ordinary virtual keys - never by taking its DRM or touch device.

## dev-muhammad-adel/react-drm-for-touchbar

- This is directly aimed at Linux T2 MacBooks. It requires the `appletbdrm` and `hid-appletb-bl` kernel modules, `video` and `input` access, and says it replaces `tiny-dfr`, `mac-touchbar-plus`, and other Touch Bar daemons. That explicit exclusion is decisive for coexistence. [README](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/README.md)
- Renderer/dependencies: a TypeScript/React custom renderer (`react-reconciler`, Yoga) with a native Node addon built using C++/node-gyp; output goes through Cairo and libdrm/KMS. Its browser preview deliberately streams the same Cairo framebuffer, not a second DOM renderer. [package manifest](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/package.json) · [native DRM source](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/native/src/drm.cpp) · [Cairo renderer](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/native/src/cairo_renderer.cpp) · [README](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/README.md)
- Input ownership is similarly direct: native code reads the Touch Bar event device and handles one primary multitouch contact; UI actions inject keys with uinput. It also watches a keyboard device for global shortcuts. This is incompatible with another service trying to own the same low-level inputs. [touch reader](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/native/src/touch_input.cpp) · [key injector](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/native/src/key_injector.cpp)
- Hyprland is a supported active-window backend through its IPC socket. The source describes only application-aware controls, not a general adapter protocol. [README](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/README.md)
- Lifecycle is unusually complete: an unprivileged systemd **user** service attaches at graphical-session start, uses a logind delay inhibitor to quiesce for suspend, reattaches on resume, and runs a detach helper at logout to restore the firmware function strip. [service unit](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/system/react-drm.service) · [README](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/README.md)
- License/maturity: GPL-3.0-or-later and version `0.1.0`; it was created June 2026 and is therefore young despite its broad feature set. Its installer can purge competing daemons and changes packages/rules/groups, so evaluate it in a reversible test setup first. [repository metadata](https://api.github.com/repos/dev-muhammad-adel/react-drm-for-touchbar) · [package manifest](https://github.com/dev-muhammad-adel/react-drm-for-touchbar/blob/master/package.json)

## dev-muhammad-adel/mac-touchbar-plus

- This repository is a fork of `tiny-dfr`, with the upstream fork network rooted in `AsahiLinux/tiny-dfr`; its default branch is `app5`, and its most recent push was October 2025. The correct reading is a forked experimental/older alternative, not a separate architecture to combine with tiny-dfr. [repository metadata](https://api.github.com/repos/dev-muhammad-adel/mac-touchbar-plus)
- It is MIT licensed, Rust, and inherits the same single direct-renderer category. Running it beside `tiny-dfr` or react-drm has the same ownership collision risk. [repository metadata](https://api.github.com/repos/dev-muhammad-adel/mac-touchbar-plus)

## stephenleo/OpenMicro

- OpenMicro is a Node 22+ game-controller bridge, not a Touch Bar driver: it uses `node-hid`, `node-pty`, and optional DualSense output. The README is macOS-first and says other platforms are not yet tested, so it is not a deployment candidate for Intel/T2 Linux. [README](https://github.com/stephenleo/OpenMicro/blob/main/README.md) · [package manifest](https://github.com/stephenleo/OpenMicro/blob/main/package.json)
- Its useful design lesson is lifecycle/state isolation: a controller API exposes normalized input; `start()`/`stop()` are idempotent; disconnect triggers reconnect polling; a `Harness` interface resolves only verified actions and can return `null` for unsupported controls. The first process owns the controller, later processes register as clients, and focus is explicit. [README](https://github.com/stephenleo/OpenMicro/blob/main/README.md)
- This supports a Touch Bar design where a single broker owns the physical panel, while Hyprland/Codex/etc. are adapters that publish state and capabilities. Do not copy its platform-specific PTY/HID implementation. License: MIT. [package manifest](https://github.com/stephenleo/OpenMicro/blob/main/package.json)

## DevVig/microbridge

- Microbridge is for the Work Louder Codex Micro macropad, not the MacBook Touch Bar. It nevertheless has the clearest reusable ownership boundary: Rust daemon owns the status bus, focus policy, and device layer; integrations publish session state and never access the device. Commands go only to the focused owner that advertised that capability. [architecture](https://github.com/DevVig/microbridge/blob/main/docs/architecture.md) · [README](https://github.com/DevVig/microbridge/blob/main/README.md)
- Its focus policy is concrete and suitable to adapt: approval requests preempt, then user pinning, then frontmost-app active session, then most-recent update. On its reference macOS platform, frontmost-app detection uses `NSWorkspace`; this is not a Hyprland implementation, so a Linux port would need a Hyprland IPC focus adapter. [architecture](https://github.com/DevVig/microbridge/blob/main/docs/architecture.md)
- Its adapter protocol is socket-based NDJSON for community adapters, with first-party integrations compiled into the daemon. It uses event-driven watchers where possible and bounded polling/backoff only where hosts expose snapshots. This is a sound state/focus adapter pattern. [architecture](https://github.com/DevVig/microbridge/blob/main/docs/architecture.md) · [protocol](https://github.com/DevVig/microbridge/blob/main/docs/protocol.md)
- Linux daemon/socket support is claimed, but HID support is still phased and the product reports early public alpha `v0.3.x`; its device HID is reverse engineered. Thus borrow the architecture, not its hardware layer. It is MIT licensed. [README](https://github.com/DevVig/microbridge/blob/main/README.md) · [architecture](https://github.com/DevVig/microbridge/blob/main/docs/architecture.md)

## Recommended boundary and risk controls

1. Select exactly one physical Touch Bar owner: retain tiny-dfr for a static mapped row, or replace it with react-drm for dynamic React/Cairo UI. Do not start both, and do not let a broker open DRM, the digitizer, or uinput when the owner already does.
2. If dynamic agent state is required, make the renderer owner expose one local, permission-restricted state ingress. Put Hyprland active-window logic and agent-specific hooks in adapters. Centralize focus arbitration and capability checks before routing actions, following Microbridge/OpenMicro's patterns.
3. Treat lifecycle as part of the physical-owner contract: attach only after graphical login, detach to the firmware strip at logout, and explicitly test sleep/wake. React-drm documents this model; tiny-dfr has device-bound restart wiring but no equivalent documented systemd/logind resume contract.
4. Preserve a fallback: static keys should still work without agent hooks, Hyprland IPC, or a focused session. Revalidate on every kernel or Touch Bar firmware-related update, because DRM/input device identity and resume timing are the dominant integration risks.
